## ۱ · محصول چیست

PC MAX یک برنامهٔ دسکتاپ ویندوز برای بهینه‌سازی بازی‌های رایانه‌ای است. کاربر
اشتراک می‌خرد و در ازای آن سه چیز می‌گیرد:

| قابلیت | چه می‌کند |
|---|---|
| **تنظیمات بهینه** | برای هر بازی، تنظیمات گرافیکی پیشنهادی بر اساس سخت‌افزار کاربر |
| **Multi Frame Generation** | نصب خودکار OptiScaler / AI Optical Flow / Streamline PC MAX روی پوشهٔ بازی |
| **بهینه‌ساز ویندوز** | تغییرات رجیستری و سرویس‌های ویندوز، با امکان بازگردانی کامل |

کاتالوگ **۳۱۳ بازی** دارد، هر کدام با توضیح فارسی و انگلیسی.

مخاطب ایرانی است: رابط راست‌به‌چپ، قیمت به تومان، پرداخت از درگاه زیبال.

```
┌──────────────▼───────────────┐
│  API (Fastify + TypeScript)  │  ← تنها مرجع تصمیم‌گیری دربارهٔ دسترسی
│  ۳۱ ماژول، ۹۶ روت            │
└──┬────────────┬───────────┬──┘
   │            │           │
┌──▼───┐   ┌────▼───┐  ┌────▼────┐
│Postgres│  │ Redis  │  │ volume  │
│۳۷ جدول │  │ کش،صف  │  │ فایل‌ها │
└────────┘  └────────┘  └─────────┘
```

**اندازهٔ کد:** حدود ۹۷ هزار خط TypeScript و Rust.

**مخزن:** monorepo با npm workspaces —
`apps/api`، `apps/desktop`، `packages/validation`، `packages/types`.

`packages/validation` قراردادهای Zod را نگه می‌دارد که هم سرور و هم کلاینت از
آن استفاده می‌کنند. یعنی اگر شکل یک پاسخ عوض شود، هر دو طرف در زمان کامپایل
خطا می‌دهند نه در زمان اجرا.

## ۳ · برنامهٔ دسکتاپ

**فناوری:** Tauri v2 — هستهٔ Rust با رابط وب (React 18 + TypeScript + Vite +
Tailwind).

**۲۲ صفحه:**

| گروه | صفحات |
|---|---|
| ورود | `Login`، `Register`، `ForgotPassword` |
| کاتالوگ | `Home`، `Games`، `GameDetail`، `Categories`، `Recommended`، `RecentlyViewed`، `Favorites` |
| کتابخانه | `Library` (بازی‌های نصب‌شدهٔ کاربر) |
| بهینه‌سازی | `OptimizedSetting`، `WindowsOptimizer` |
| MFG | `MultiFrameGeneration`، `OptiScaler`، `AiOpticalFlow`، `StreamlinePcMax`، `OptiFlow` |
| حساب | `Subscription`، `Settings`، `About` |
| مدیریت | `Admin` (شامل ۱۱ تب) |

### چرا بخشی از آن Rust است

هر چیزی که روی دیسک کاربر می‌نویسد در Rust است، نه در جاوااسکریپت:

- `optiflow.rs` — نصب و حذف فایل‌های ابزارهای MFG داخل پوشهٔ بازی
- `winopt.rs` — تغییرات رجیستری و سرویس‌های ویندوز، با snapshot و بازگردانی
- `lib.rs` — دستورهای Tauri که پل میان رابط و این دو هستند

دلیلش امنیت است: مسیر مقصد فایل‌ها از سرور نمی‌آید بلکه از انتخاب کاربر
(فایل اجرایی بازی) استخراج می‌شود، و همان‌جا که استخراج می‌شود باید بررسی شود.
جزئیات در بخش [مدل امنیتی](#۹--مدل-امنیتی).

### آفلاین بودن

کاتالوگ روی دیسک کش می‌شود. اگر سرور در دسترس نباشد، برنامه با محتوای کش‌شده
کار می‌کند و کاربر را به صفحهٔ ورود پرت نمی‌کند — نشانگر بالای صفحه تفاوت
«اینترنت قطع است» و «سرویس در دسترس نیست» را نشان می‌دهد، چون این دو معنای
متفاوتی برای کاربر دارند.

## ۴ · سرور API

**فناوری:** Fastify + TypeScript + Drizzle ORM + PostgreSQL + Redis.

**۳۱ ماژول، ۹۶ روت.** ماژول‌ها بر اساس دامنه جدا شده‌اند:

| گروه | ماژول‌ها |
|---|---|
| عمومی | `public-games`، `public-optimizations`، `public-optimized-setting`، `system`، `sync` |
| احراز هویت | `auth` (ادمین)، `auth-user` (کاربر) |
| کاربر | `users`، `favorites`، `device`، `hardware`، `client-errors` |
| تجاری | `subscriptions`، `payments` |
| محتوا | `packages`، `mfg-tools`، `uploads` |
| مدیریت | ۱۴ ماژول `admin-*` |

### چند تصمیم مهم

**قراردادها با Zod.** هر روت ورودی و خروجی‌اش را با Zod توصیف می‌کند. یعنی
بدنهٔ نامعتبر با ۴۰۰ رد می‌شود نه با ۵۰۰، و مستندات OpenAPI خودکار تولید
می‌شوند (`/docs`).

**کش با TTL.** داده‌های نیمه‌ثابت (کاتالوگ، پلن‌ها، تنظیمات) از Redis کش
می‌شوند و اگر Redis نباشد به کش درون‌حافظه‌ای برمی‌گردند. نبودن کش هیچ‌وقت
نباید بالا آمدن API را متوقف کند.

**صف ایمیل.** ثبت‌نام منتظر ارسال واقعی SMTP نمی‌ماند. کد ذخیره می‌شود، پاسخ
برمی‌گردد، و یک worker در پس‌زمینه ارسال می‌کند (لیست Redis + `BRPOP`، چهار
تلاش با backoff). اگر تحویل نهایتاً شکست بخورد کد **حذف** می‌شود، نه علامت‌گذاری
— وگرنه cooldown ارسال مجدد کاربر را پشت کدی که هرگز نرسیده نگه می‌داشت.

**پاک‌سازی خودکار.** کدهای منقضی، تلاش‌های ناموفق ورود، نشست‌های مرده و
رویدادهای بازدید قدیمی به‌صورت دوره‌ای حذف می‌شوند (`RETENTION_INTERVAL_HOURS`).

## ۶ · احراز هویت و نشست‌ها

دو سیستم کاملاً جدا: **کاربر** و **ادمین**. توکن‌هایشان با `kind` نشانه‌گذاری
می‌شوند تا توکن ادمین هرگز به‌جای توکن کاربر کار نکند، حتی با اینکه راز امضا
مشترک است.

### ثبت‌نام

```
کاربر ایمیل می‌دهد
  → کد شش‌رقمی از CSPRNG ساخته می‌شود
  → فقط هش کد ذخیره می‌شود
  → کد در صف ایمیل می‌رود، پاسخ فوراً برمی‌گردد
کاربر کد + رمز می‌دهد
  → حساب ساخته می‌شود، نشست باز می‌شود
```

**محافظت‌ها:**

- **cooldown ارسال مجدد** به‌ازای هر شناسه، در دیتابیس — اسپم کردن کد به یک
  ایمیل مستقل از IP جلوگیری می‌شود
- **قفل حساب** بعد از چند تلاش ناموفق ورود
- **هش با Argon2id** (اندازه‌گیری‌شده: حدود ۱۱ میلی‌ثانیه با موازی‌سازی)
- **هش تقلبی** وقتی حسابی وجود ندارد، تا زمان پاسخ ورود ناموفق با ورود با رمز
  غلط یکسان باشد — وگرنه می‌شد فهمید کدام ایمیل‌ها ثبت شده‌اند

### توکن‌ها

- **access token** کوتاه‌عمر، هرگز روی دیسک ذخیره نمی‌شود
- **refresh token** در کوکی `httpOnly`
- `tokenVersion` روی هر کاربر: با تغییر رمز یا بستن حساب یک واحد بالا می‌رود و
  **همهٔ** توکن‌های صادرشده را می‌کشد، نه فقط نشست فعلی

### rate limit

شمارنده‌ها روی Redis‌اند تا اگر روزی چند نمونهٔ API اجرا شود، سقف‌ها ضرب نشوند.
کلید شمارش برای درخواست‌های احراز هویت‌شده **شناسهٔ کاربر** است نه IP — چون
اپراتورهای موبایل ایران هزاران مشترک را پشت یک IP می‌گذارند و شمارش بر اساس IP
یعنی مسدود کردن کاربران واقعی در روز شلوغ.

### بستن حساب

`DELETE /me` — با تأیید رمز فعلی. ایمیل، شماره، نام کاربری، رمز، دستگاه‌ها و
علاقه‌مندی‌ها پاک می‌شوند. **پرداخت‌ها می‌مانند** چون سند مالی‌اند. شناسه‌ها به
`null` تبدیل می‌شوند نه رشتهٔ خالی، پس ایندکس یکتا آزاد می‌شود و همان شخص
می‌تواند دوباره ثبت‌نام کند.

## ۷ · اشتراک و پرداخت

### پلن‌ها

چهار پلن: ۱، ۳، ۶ و ۱۲ ماهه. قیمت‌ها در دیتابیس به **ریال** ذخیره و شارژ
می‌شوند؛ رابط کاربری آن‌ها را به **تومان** نشان می‌دهد (تقسیم بر ده، فقط در
نمایش).

هر پلن `deviceLimit` دارد که **سمت سرور** اجرا می‌شود
(`assertDeviceSlotAvailable`)، نه در رابط کاربری.

### جریان خرید

```
برنامه  →  POST /subscriptions/purchase
سرور    →  یک ردیف پرداخت می‌سازد، از درگاه آدرس می‌گیرد
برنامه  →  مرورگر سیستم را روی آن آدرس باز می‌کند
کاربر   →  در زیبال پرداخت می‌کند
درگاه   →  به callbackUrl برمی‌گردد
سرور    →  خودش از درگاه verify می‌کند، مبلغ را می‌سنجد، بعد فعال می‌کند
```

**فعال‌سازی هیچ‌وقت به callback اعتماد نمی‌کند.** سرور مستقل از درگاه می‌پرسد
پرداخت شده یا نه، و مبلغ گزارش‌شده را با قیمت پلن مقایسه می‌کند. یعنی باز کردن
دستی آدرس بازگشت اشتراک نمی‌دهد.

### تمدید

خرید دوباره وقتی اشتراک فعال است، **به زمان باقی‌مانده اضافه می‌کند**. قبلاً از
امروز حساب می‌شد و زمان پرداخت‌شده بی‌صدا از بین می‌رفت. ردیف قبلی در همان
تراکنش بازنشسته می‌شود تا همیشه دقیقاً یک اشتراک فعال باشد.

### زنجیرهٔ زیبال — سه تلهٔ واقعی

این بخش را با دقت بخوان؛ هر سه مورد در عمل اتفاق افتادند.

**۱. درگاه دامنهٔ callback را اجبار می‌کند.** مرچنت روی `cianet.ir` تأیید شده
ولی API روی `pc-maxapp.rixy.ir` است. زیبال با `result: 106` رد می‌کند. راه‌حل:
زیردامنهٔ `pay.cianet.ir` با CNAME پروکسی‌شده از کلادفلر به API.

**۲. کلادفلر با HTTPS به مبدأ وصل می‌شود.** اگر vhost فقط `listen 80` داشته
باشد، هیچ بلوکی روی ۴۴۳ با آن نام پیدا نمی‌شود و nginx به سایت پیش‌فرض
می‌افتد — از بیرون دقیقاً شبیه «پروکسی کار نمی‌کند» است. راه‌حل: SSL روی همان
سایت فعال شود (self-signed کافی است، چون کلادفلر در حالت Full اعتبارسنجی
نمی‌کند).

**۳. زیبال با `Referer` خالی تراکنش را رد می‌کند.** آدرس درگاه که مستقیم به
سیستم‌عامل داده شود، هیچ صفحه‌ای مبدأ نیست و Referer خالی می‌رود. راه‌حل: یک
صفحهٔ واسط روی `pay.cianet.ir` که مرورگر از آن به درگاه می‌رود. و چون `helmet`
روی همهٔ پاسخ‌ها `referrer-policy: no-referrer` می‌گذارد، این هدر برای همان یک
روت به `origin` تغییر داده شده.

**صفحهٔ بعد از پرداخت.** مرورگر صفحهٔ فارسی می‌گیرد («پرداخت با موفقیت انجام
شد» / «پرداخت تأیید نشد»)، ولی برنامه و `curl` و سوئیت e2e همان JSON قبلی را
می‌گیرند — تفکیک بر اساس هدر `Accept`.

### درگاه‌های پشتیبانی‌شده

`mock` (تست) · `zarinpal` · `zibal` (فعال) · `idpay`

همه پشت یک `PaymentProvider` interface‌اند، پس افزودن درگاه تازه یعنی پیاده‌سازی
دو متد، بدون دست زدن به منطق اشتراک.

## ۸ · پکیج‌های بهینه‌سازی و ابزارهای MFG

### مدل داده

هر پکیج مجموعه‌ای از فایل است، و هر فایل سه ویژگی تعیین‌کننده دارد:

| ویژگی | معنی |
|---|---|
| `component` | کدام انتخاب کاربر این فایل را می‌آورد (`installer`, `plan`, `order`, `unlocker`, `streamline`) |
| `variant` | نام آن انتخاب؛ `null` یعنی فایل پایه که همیشه می‌آید |
| `role` | کجا نوشته شود: `relative` (مسیر زیر پوشهٔ بازی)، `launcher` (کنار فایل اجرایی)، `streamline` (جایگزینی هر کپی موجود) |

### جریان نصب

```
کاربر ابزار و گزینه‌هایش را انتخاب می‌کند
  → POST /mfg/tools/:tool/download   (نیازمند اشتراک، سمت سرور)
  → سرور آدرس‌های امضاشدهٔ کوتاه‌عمر برمی‌گرداند
کلاینت فایل‌ها را می‌گیرد و هش هرکدام را می‌سنجد
  → optiflow_install (Rust)
     ۱. staging و بررسی هش
     ۲. بکاپ از فایل‌های اصلی داخل پوشهٔ بازی
     ۳. نوشتن اتمیک
     ۴. اگر هر مرحله شکست بخورد، کل دسته rollback می‌شود
```

### دو بهینه‌سازی مهم در دانلود

پکیج OptiScaler **۴۲۳.۸ مگابایت در ۳۱ فایل** بود، ولی:

- **۱۷۱ مگابایتش تکراری بود.** هشت فایل با یک `sha256` مشترک — همان باینری زیر
  هشت نام DLL مختلف تا هر بازی هرکدام را لود می‌کند پیدا کند. حالا هر بایت یکتا
  **یک بار** دانلود و **یک بار** از IPC رد می‌شود، و در هر هشت مقصد نوشته
  می‌شود. دانلود شد **۲۵۲.۸ مگابایت**.
- **TTL آدرس‌ها مهلت کل دسته بود.** هر ۳۱ آدرس در یک لحظه امضا می‌شدند با
  اعتبار ۱۵ دقیقه؛ روی خط کند، آدرس‌های آخر قبل از نوبتشان منقضی می‌شدند و کل
  نصب می‌افتاد. حالا آدرس منقضی یک درخواست امضای دوباره هزینه دارد، نه کل نصب.

### حذف

رکورد نصب روی همان ماشین نگه داشته می‌شود (`mfgInstalls`) و حذف **دقیقاً** همان
فایل‌ها را برمی‌گرداند — هیچ‌وقت با حدس زدن از روی نام فایل کار نمی‌کند. فایلی
که جایگزین شده از بکاپ برمی‌گردد؛ فایلی که تازه اضافه شده حذف می‌شود.

## ۹ · مدل امنیتی

### اصل حاکم

**کلاینت هیچ‌وقت تصمیم نمی‌گیرد کاربر چه چیزی می‌تواند داشته باشد.**

رابط کاربری ممکن است قفل را باز نشان دهد، ولی سرور مستقل تصمیم می‌گیرد.
دستکاری برنامه فقط ظاهر قشنگ‌تری می‌دهد و هیچ فایلی نمی‌آورد.

### آنچه تأیید شده (تست‌شده روی پروداکشن)

| آزمایش | نتیجه |
|---|---|
| `GET /uploads/packages/…` بدون امضا | `403` |
| فهرست دایرکتوری `/uploads/` | `404` |
| `POST /mfg/tools/…/download` بدون ورود | `401` |
| متادیتای عمومی پکیج | هیچ آدرس یا `storageKey` — فقط نام و هش و مقصد |

### لایه‌ها

**دسترسی به فایل.** آدرس‌های دانلود با HMAC امضا و زمان‌دار می‌شوند
(`DOWNLOAD_SIGNING_SECRET`). فایل‌های پکیج از مسیر عمومی سِرو نمی‌شوند — یک hook
هر درخواست به `/uploads/packages/` را با ۴۰۳ رد می‌کند.

**دسترسی به قابلیت.** `requireFeature('multi_frame_generation')` قبل از هر
دانلود، اشتراک را از دیتابیس می‌سنجد.

**نوشتن روی دیسک (Rust).** سه قانون بدون استثنا:

1. مقصد باید داخل پوشهٔ بازی باشد — بررسی بعد از canonicalize کردن مسیرها، تا
   یک symlink نتواند بیرون اشاره کند
2. نام فایل از فهرست پسوندهای مجاز رد شود — هیچ‌وقت چیزی اجرایی نوشته نمی‌شود
3. فایل `streamline` فقط **جایگزین** می‌شود؛ اگر بازی آن جزء را نداشته باشد،
   چیزی ساخته نمی‌شود

`safe_destination` مسیرهای `..`، مطلق، بک‌اسلش، کولن (درایو ویندوز و NTFS
alternate data stream) و dotfile را رد می‌کند.

**ریسک باقی‌مانده — و راه‌حل نرم‌افزاری ندارد.** وقتی یک مشترک واقعی فایل‌ها را
دانلود کرد، آن‌ها دست اوست و می‌تواند پخششان کند. اهرم واقعی سقف دستگاه و
تشخیص اشتراک‌گذاری حساب است، نه قفل روی فایل.

داخل همان برنامهٔ دسکتاپ، مسیر `#/admin`، با ورود جدا از حساب کاربری.

**۱۱ تب:**

`Dashboard` · `Games` · `Packages` · `Profiles` · `Users` · `Admins` ·
`Taxonomy` · `Releases` · `Settings` · `Audit` · `Crashes`

### کارهای پرکاربرد

**ویرایش بازی** — نام، اسلاگ، تگ‌لاین، **دو کادر توضیحات** (فارسی و انگلیسی،
هرکدام با جهت متن درست)، سازنده، ناشر، موتور، API، تصاویر، حداقل سیستم.

**جایگزینی فایل‌های یک ابزار** — قبلاً برای OptiScaler یعنی ۳۱ بار تأیید حذف و
۳۱ بار آپلود با تایپ دستی مقصد. حالا:

1. تیک «انتخاب همه» → حذف با یک تأیید
2. انتخاب همهٔ فایل‌های جدید → آپلود دسته‌ای که نام خود فایل را مقصد می‌گیرد

اگر وسط کار خطا بدهد می‌گوید چندتا انجام شده — تفاوت «بقیه را دوباره بزن» با
«از اول شروع کن».

**ثبت نسخهٔ جدید** — تب `Releases`. البته با CI این خودکار انجام می‌شود.

**گزارش تغییرات** — تب `Audit` هر عمل مدیریتی را با شناسهٔ ادمین ثبت می‌کند.

```
        │
        ▼

```

### secretهای لازم

| نام | برای چه |
|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | امضای نصاب — بدونش آپدیت خودکار نصاب را قبول نمی‌کند |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | رمز همان کلید |
| `PCMAX_ADMIN_PASSWORD` | ثبت خودکار نسخه در سرور |

**تلهٔ تاریخی:** مرحلهٔ ثبت وقتی secret نبود `exit 0` می‌داد — یعنی skip که
دقیقاً شبیه success گزارش می‌شد. نسخه‌های ۰.۴.۲ و ۰.۴.۳ سبز منتشر شدند در حالی
که هر کاربری همچنان ۰.۴.۱ را آخرین نسخه می‌دید. حالا نبودِ secret روی این مخزن
بیلد را **قرمز** می‌کند.

### قرارداد به‌روزرسانی

سرور به `GET /updates/:target/:arch/:currentVersion` یا `204` می‌دهد (به‌روز
هستی) یا `200` با `{version, url, signature, pub_date}`. اگر امضا نباشد، سرور
آن نسخه را «آپدیتی موجود نیست» حساب می‌کند — یعنی بی‌صدا هیچ‌چیز عرضه نمی‌کند.

## ۱۳ · بکاپ و بازیابی از فاجعه

سند کامل: [`DISASTER-RECOVERY.md`](DISASTER-RECOVERY.md)

### سه چیزی که باید نگه داشته شوند

| | بدونش چه می‌شود |
|---|---|
| **دیتابیس** | کاربران، اشتراک‌ها، پرداخت‌ها، کاتالوگ — همه رفته |
| **فایل‌های پکیج** (volume داکر) | API بالا می‌آید، کاربر وارد می‌شود، و **هیچ دانلودی کار نمی‌کند** |
| **`infrastructure/.env`** | همهٔ لینک‌های صادرشده و نشست‌های باز باطل می‌شوند |

```bash
pcmax backup-all
```

هر سه را در یک آرشیو می‌گذارد و **خودش را تأیید می‌کند**: تعداد ردیف‌های
دیتابیس و فایل‌های آرشیو را می‌شمارد، و مهم‌تر — بررسی می‌کند هر `storage_key`
که دیتابیس به آن ارجاع می‌دهد واقعاً فایلش در آرشیو باشد. دو نیمه‌ای که هرکدام
جداگانه سالم باشند ولی با هم نخوانند، به کاتالوگی بازیابی می‌شوند که به
فایل‌های ناموجود اشاره می‌کند.

> **بکاپ روی همان دیسکی که محافظت می‌کند، بکاپ نیست.** آرشیو را از سرور بیرون
> بکش.

### آنچه هیچ بکاپی نجات نمی‌دهد

کلید امضای به‌روزرسانی در secretهای گیت‌هاب است، نه روی سرور. اگر آن مخزن از
دست برود، هیچ نسخهٔ جدیدی را نصب‌های موجود قبول نمی‌کنند — چون کلید عمومی
متناظرش داخل خودِ برنامه کامپایل شده.

## ۱۴ · تست‌ها

| سوئیت | تعداد | چه چیزی را می‌سنجد |
|---|---|---|
| API (vitest) | **۲۲۶** | یکپارچه با Postgres واقعی: احراز هویت، پرداخت، اشتراک، پکیج، صفحه‌بندی، نگهداشت |
| دسکتاپ (vitest) | **۱۲۱** | منطق کلاینت: قیمت‌گذاری، دانلود، کش، ترجمه |
| Rust (cargo) | **۷۵** | نصب و حذف روی فایل‌سیستم واقعی — هیچ mock‌ی |
| e2e | **۹۰** | فقط HTTP، روی هر استقراری قابل اجرا |

سوئیت e2e دو حالت دارد: `readonly` (بی‌خطر روی پروداکشن) و `full` (که عمداً
روی هر آدرسی جز localhost اجرا نمی‌شود).

تست‌های Rust روی فایل‌سیستم واقعی کار می‌کنند و هر تست ابتدا در برابر نسخه‌ای
از کد **بدون** محافظ مربوطه شکست خورده — یعنی ثابت شده که واقعاً چیزی را
می‌سنجد.

## ۱۵ · محدودیت‌ها و کارهای انجام‌نشده

صادقانه، چون دانستنش بهتر از کشف کردنش در بدترین لحظه است.

**یک نمونهٔ API.** یک کانتینر، یک پروسهٔ Node (تک‌رشته‌ای). ظرفیت افقی صفر است و
هر کرش یعنی قطعی کامل تا بالا آمدن دوباره. زیرساختش آماده است (rate limit روی
Redis، صف ایمیل با BRPOP، تنظیم استخر دیتابیس) ولی چون استقرار روی شبکهٔ میزبان
است، مقیاس افقی یک تغییر توپولوژی است نه یک عدد. مسیرش در
[`PRODUCTION.md`](PRODUCTION.md).

**متادیتای کاتالوگ خالی است.** از ۳۱۳ بازی، سال انتشار، موتور، API گرافیکی،
کاور، سازنده و حداقل سیستم برای **هیچ‌کدام** پر نشده. فقط نام، ژانر و توضیحات.

**کپچا ندارد.** عمدی: کپچای گوگل در ایران بدون فیلترشکن لود نمی‌شود، یعنی برای
کاربر واقعی ثبت‌نام را می‌شکند نه برای ربات. محافظت فعلی cooldown ارسال کد و
قفل حساب است.

**کپی خارج از سرور دستی است.** cron شبانه بکاپ کامل می‌گیرد ولی روی همان دیسک؛
بیرون کشیدنش هنوز کار دست است.

**رشته‌های خطای `winopt.rs`** هنوز انگلیسی‌اند. خطاهای `optiflow.rs` ترجمه
شده‌اند.
