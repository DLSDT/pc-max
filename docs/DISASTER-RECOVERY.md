# اگر سرور از دست رفت

چه چیزی نگه داشته می‌شود، کجا، و چطور روی یک ماشین تازه برمی‌گردد.

---

## آنچه باید نگه داشته شود

سه چیز، و **هر سه لازم‌اند**. دو تای اول بدون سومی هم بی‌فایده‌اند.

| | کجاست | بدونش چه می‌شود |
|---|---|---|
| **دیتابیس** | Postgres در کانتینر | کاربران، اشتراک‌ها، پرداخت‌ها، کاتالوگ — همه رفته |
| **فایل‌های پکیج** | volume داکر `*_uploads` | API بالا می‌آید، کاربر وارد می‌شود، و **هیچ دانلودی کار نمی‌کند**: هر ردیف پکیج به کلیدی اشاره می‌کند که دیگر فایلی پشتش نیست |
| **`infrastructure/.env`** | فقط روی همان سرور | `DOWNLOAD_SIGNING_SECRET` و `JWT_ACCESS_SECRET` را از دست بدهی، همهٔ لینک‌های صادرشده و همهٔ نشست‌های باز باطل می‌شوند و هر کاربر باید دوباره وارد شود |

```bash
pcmax backup-all
```

هر سه را در یک آرشیو می‌گذارد و آدرسش را چاپ می‌کند.

> **`pcmax backup` این کار را نمی‌کند.** آن فقط دیتابیس است. مدت‌ها تنها بکاپ موجود همان بود، یعنی فایل‌های پکیج هیچ نسخهٔ دومی نداشتند.

---

## نکته‌ای که بکاپ را بی‌ارزش می‌کند

بکاپ روی همان دیسکی که محافظت می‌کند، بکاپ نیست. `/www/pcmax-backups` با سرور می‌میرد.

**آرشیو را از ماشین بیرون بکش:**

```bash
scp root@<server>:/www/pcmax-backups/pcmax-full-*.tar.gz .
```

هر جای دیگری — هارد اکسترنال، فضای ابری، ماشین خودت. فقط نه همان سرور.

## بازیابی روی یک VPS تازه

```bash
# ۱ · داکر و مخزن
git clone git@github.com:DLSDT/pc-max.git /www/pcmax
cd /www/pcmax/infrastructure

# ۲ · آرشیو را باز کن
mkdir -p /tmp/restore && tar xzf pcmax-full-<تاریخ>.tar.gz -C /tmp/restore
cp /tmp/restore/env .env          # همان رازها، وگرنه نشست‌ها و لینک‌ها می‌میرند

# ۳ · بالا آوردن
ln -sf /www/pcmax/infrastructure/pcmax /usr/local/bin/pcmax
pcmax up

# ۴ · فایل‌ها را به volume برگردان
VOL=$(docker volume ls -q | grep -E 'uploads$' | head -1)
docker run --rm -v "$VOL":/data -v /tmp/restore:/in alpine \
  tar xzf /in/uploads.tgz -C /data

# ۵ · دیتابیس
pcmax restore /tmp/restore/db.json
pcmax fix-sequences        # وگرنه اولین insert روی کلید اصلی می‌شکند

# ۶ · بررسی
pcmax health
```

بعد DNS را به IP جدید بده. اگر از کلادفلر استفاده می‌کنی، فقط رکورد A عوض می‌شود.

## آنچه بکاپ **نمی‌تواند** نجات دهد

**کلید امضای به‌روزرسانی** در secretهای گیت‌هاب است (`TAURI_SIGNING_PRIVATE_KEY`)، نه روی سرور. اگر آن مخزن را از دست بدهی، هیچ نسخهٔ جدیدی را نصب‌های موجود قبول نمی‌کنند — چون کلید عمومیِ متناظرش داخل خودِ برنامه کامپایل شده. آن secret باید جدا نگه داشته شود.

**درگاه پرداخت** به دامنه گره خورده، نه به سرور. مادامی که `pay.cianet.ir` را به IP جدید بدهی، پرداخت‌ها بی‌وقفه ادامه می‌یابند.

## خودکارسازی

```bash
crontab -l 2>/dev/null | cat - infrastructure/backup.cron | crontab -
crontab -l    # تأیید کن که واقعاً نشسته
```

آن دستور دوم مهم است: فایل cron در مخزن بودن یعنی *قابل نصب*، نه *نصب‌شده*. یک بار چک کن.

کپیِ خارج از سرور همچنان دستی است. ساده‌ترین حالت، یک cron روی ماشین خودت که شبانه `scp` بزند.
